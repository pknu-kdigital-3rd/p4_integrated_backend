# Docker operations, required settings, and reloads

This is the operational reference for testing the stack with Docker Desktop on
Windows first and then deploying it with Docker Engine on Linux. Run every
Compose command from the repository root, where `docker-compose.yml` exists.

## Supported Compose files

| File | Use | Source changes | GPU |
|---|---|---|---|
| `docker-compose.yml` | Production-like images | Rebuild/recreate the affected service | NVIDIA GPU required by Vision |
| `docker-compose.dev.yml` | Local development | Node, routing, and Vision source reload automatically | NVIDIA GPU required by Vision |

The development file still uses the compiled relay image. It does not provide
Go hot reload.

## Host prerequisites

### Windows test host

- Docker Desktop using Linux containers and the WSL2 backend.
- A current NVIDIA Windows driver with Docker Desktop GPU support enabled.
- The Docker Desktop GPU check must succeed:

  ```powershell
  docker run --rm --gpus all nvidia/cuda:13.0.0-runtime-ubuntu24.04 nvidia-smi
  ```

- Open the public ports in Windows Firewall when clients connect from another
  device.
- Run from a normal local checkout. Compose paths such as `./data/tls` and
  `./services/vision/models` are resolved relative to the checkout.

### Linux deployment host

- Docker Engine and the Compose plugin.
- NVIDIA Container Toolkit and a working `nvidia-smi` check.
- The same model and routing data files described below.

With one visible GPU, the Vision entrypoint selects that device and exposes it
to the application as `cuda:0`. With multiple visible GPUs it selects the last
one. Check the Vision log for the selected device.

## Compose credentials

The production Compose file requires these four variables from the host. The
development Compose file uses fixed development-only values so a local stack
can start without a shell environment or an env file. Do not reuse the
development values outside a local development stack.

| Variable | Used by | Production requirement |
|---|---|---|
| `NODE_INTERNAL_SERVICE_TOKEN` | Node, relay, Vision | One identical random value everywhere; at least 32 characters and must not start with `replace-`. |
| `MINIO_ROOT_PASSWORD` | MinIO and MinIO bootstrap | The MinIO root password used when the data directory is first initialized. Keep it stable for existing `data/minio_data`. |
| `MINIO_SECRET_KEY` | Relay and MinIO bootstrap | Relay bucket-account secret; at least 12 characters and must not start with `replace-`. |
| `MINIO_NODE_SECRET_KEY` | Node and MinIO bootstrap | Node bucket-account secret; at least 12 characters and must not start with `replace-`. |

The MinIO access-key names are fixed in Compose (`p4-minio-root`, `p4-relay`,
and `p4-node`). In development, the corresponding fixed secrets are shared by
the services automatically. In production, only the secrets above are
required from the host.

The host address and BIMS key are not absolute requirements:

| Variable | Default | When needed |
|---|---|---|
| `TLS_PUBLIC_ADDRESS` | `10.174.96.119` | Set this when the Docker host has another client-reachable address. It controls the TLS certificate SAN, public URLs, MinIO playback URLs, TURN URL, and Coturn relay/external address. |
| `BUSAN_BIMS_SERVICE_KEY` | empty | Required only when the operator selects **Live BIMS**. Replay mode works without it. Compose forwards it to routing; it is not baked into an image. |

Other commonly changed values are optional: `YOLO_MODEL`, `YOLO_DEVICE`,
`YOLO_USE_LAST_GPU`, `ANDROID_TELEMETRY_ENABLED`, `TURN_URL`,
`TURN_USERNAME`, `TURN_PASSWORD`, and the recording queue/sample settings.
The Compose defaults are used when they are omitted.

### Supplying production secrets without shell residue

Use an ignored file outside the repository and pass it explicitly on each
Compose command. Do not commit it:

```text
NODE_INTERNAL_SERVICE_TOKEN=<random-value-at-least-32-characters>
MINIO_ROOT_PASSWORD=<minio-root-secret>
MINIO_SECRET_KEY=<relay-secret-at-least-12-characters>
MINIO_NODE_SECRET_KEY=<node-secret-at-least-12-characters>
TLS_PUBLIC_ADDRESS=10.174.96.119
BUSAN_BIMS_SERVICE_KEY=<live-bims-key-if-needed>
```

Windows production example:

```powershell
docker compose --env-file C:\secure\p4-compose.env -f docker-compose.prod.yml up -d --build
```

Linux example:

```bash
docker compose --env-file /etc/p4/compose.env up -d --build
```

For development testing, use `docker-compose.dev.yml` without the four secret
variables above. Existing `data/minio_data` must have been initialized with the
fixed development root password, or MinIO will continue to require its old
root password. For playback-only testing, omit `BUSAN_BIMS_SERVICE_KEY`.
`TLS_PUBLIC_ADDRESS`
may also be omitted when `10.174.96.119` is the correct host address.

## Required repository artifacts and first startup

The following files are not generated by Compose:

- `services/routing-tracking/busan-roads_osm.pbf` for routing startup;
- `services/vision/models/a4_best.engine` for the default Vision model;
- the custom implementation under `services/vision/.ultralytics-custom`;
- the Node package's private Git dependency, which requires a BuildKit SSH agent
  with access to the dependency repository during the first image build;
- optional BIMS history files under `services/routing-tracking/data` for replay
  vehicle positions.

The `services/vision/models` directory is intentionally ignored by Git. Copy
the model onto each host; do not expect `git pull` to provide it.

### Convert a PyTorch checkpoint to TensorRT

The default Compose model is `services/vision/models/a4_best.engine`. If only
the checkpoint is available, copy it to
`services/vision/models/a4_best.pt` and run the exporter on the GPU host that
will run Vision. The exporter uses the custom Ultralytics checkout configured by
the Vision project and produces `a4_best.engine` beside the checkpoint:

```powershell
Set-Location services/vision
uv sync --locked
uv run python export_tensorrt.py --model models/a4_best.pt --device 0 --imgsz 640
```

On Linux, run the same command from `services/vision`:

```bash
cd services/vision
uv sync --locked
uv run python export_tensorrt.py --model models/a4_best.pt --device 0 --imgsz 640
```

The export environment must have CUDA-enabled PyTorch and the TensorRT Python
bindings installed. The script stops with a diagnostic if either is missing.
Use `--force` to replace an existing engine, `--precision fp32` for an FP32
engine, or `--keep-onnx` to retain the intermediate ONNX file. TensorRT engines
are compiled for the GPU and TensorRT runtime used during export; regenerate the
engine when moving to an incompatible GPU or runtime version.

Start the production-like stack:

```bash
docker compose --env-file <secrets-file> up -d --build
```

Start the development stack:

```bash
docker compose --env-file <secrets-file> -f docker-compose.dev.yml up -d --build
```

The first startup initializes JWT keys and the self-signed TLS certificate in
`data/jwt` and `data/tls`, runs Prisma migrations/seed, starts MinIO, and runs
the one-shot `minio-bootstrap` container. The MinIO Console is private and is
not required for replay.

### Verify and clean up MinIO bootstrap

`minio-bootstrap` is a one-shot service. A successful run ends with `Exited
(0)`; it is not supposed to keep running after it creates the bucket and
application accounts. Check its status and logs with the Compose file you are
using (`docker-compose.dev.yml` or `docker-compose.prod.yml`):

```bash
docker compose -f docker-compose.dev.yml ps -a minio-bootstrap
docker compose -f docker-compose.dev.yml logs --no-color minio-bootstrap
```

The logs should end with a message that the `p4-trip-recordings` bucket and
recording credentials are ready. After recording the logs, remove the completed
one-shot container without stopping MinIO:

```bash
docker compose -f docker-compose.dev.yml rm -f minio-bootstrap
```

Use `docker compose ... up -d minio` when only MinIO should be started. A later
`docker compose ... up -d` for the whole stack recreates and runs the bootstrap
service again; this is safe because the bootstrap script is idempotent.

## Reload and rebuild methods

### Development Compose

| Changed item | Action | Container restart? |
|---|---|---|
| Node TypeScript | Edit `node/src`; `tsx watch` reloads it | No |
| Operator web JavaScript/CSS/HTML | Edit `operator-web`; refresh the browser | No |
| Routing Python | Edit `services/routing-tracking`; Uvicorn reloads it | No |
| Vision Python | Edit `services/vision/app`; Uvicorn reloads it | No |
| Vision model contents at the same path | Replace the mounted file, then `touch services/vision/app/main.py` to trigger Vision reload | No Docker restart; Vision process reloads |
| Vision model path or `.pt`/`.engine` selection | Change `YOLO_MODEL`, then force-recreate Vision | Vision container recreated, no image rebuild |
| Go relay source | Build and recreate only relay; there is no current Go watcher | Relay container recreated |
| Nginx configuration | Run `docker exec vehicle-platform-nginx nginx -t` then `docker exec vehicle-platform-nginx nginx -s reload` | No |
| Compose environment value | `docker compose ... up -d --force-recreate <service>` | Affected container recreated |

Relay source update:

```bash
docker compose -f docker-compose.dev.yml build relay
docker compose -f docker-compose.dev.yml up -d --no-deps relay
```

Vision model replacement at the configured default path:

```bash
cp new-model.engine services/vision/models/a4_best.engine
touch services/vision/app/main.py
docker compose -f docker-compose.dev.yml logs -f vision
```

The loader supports both segmentation `.engine` and `.pt` files through
`YOLO_MODEL`. TensorRT engines skip PyTorch `.to()`/`.fuse()` setup; `.pt`
checkpoints use it. The model must still be a segmentation model. Changing the
model filename or extension requires a new `YOLO_MODEL` environment value and a
Vision container recreation.

### Production-like Compose

Production commands do not use source reloaders:

```bash
docker compose --env-file <secrets-file> up -d --build node-migrate node
docker compose --env-file <secrets-file> up -d --build routing
docker compose --env-file <secrets-file> up -d --build vision
docker compose --env-file <secrets-file> build relay
docker compose --env-file <secrets-file> up -d --no-deps relay
```

Replacing a mounted Vision model at the same path does not require an image
build, but it does require a Vision process restart:

```bash
docker compose --env-file <secrets-file> restart vision
```

Changing an environment value requires `up -d --force-recreate`; `restart`
does not replace a container's old environment. Changing Python, TypeScript,
or Go code requires rebuilding the relevant production image first.

## Windows-specific gotchas

- `TLS_PUBLIC_ADDRESS` must be the Windows host address reachable by the
  Android device/browser, not a Docker container address. Use the exact IP in
  the URL; `localhost` and `127.0.0.1` will not match the generated certificate.
- Copy `data/tls/server.crt` to Windows clients and import it into the Windows
  trusted root store (or accept the certificate per browser). Never distribute
  `data/tls/server.key`.
- Coturn uses `network_mode: host`. Docker Desktop host networking and UDP
  relay behavior depend on Docker Desktop/WSL2 version and settings. If the
  WebRTC offer works but ICE never reaches `connected`, check Docker Desktop
  host-network support and Windows Firewall for TCP/UDP ports `39004-39007`.
  Running the same Compose stack inside a Linux/WSL2 environment is the most
  predictable TURN test.
- Windows bind mounts can be slower for Uvicorn's file watcher. The manual
  `touch` reload above is reliable when a model replacement is not detected.
- Existing Linux symlinked `data` directories do not transfer as Windows
  storage mappings. Recreate the `data` subdirectories or configure Windows
  paths explicitly in Compose.

## Operational gotchas

- `docker compose down` preserves `data/`; deleting `data/minio_data` loses
  recordings, deleting `data/pgdata` loses database state, and deleting
  `data/tls`/`data/jwt` rotates trust material and signing keys.
- If MinIO root credentials change after `data/minio_data` was initialized,
  MinIO still uses the original credentials. Update the existing installation
  deliberately or migrate the data; changing the Compose value alone is not a
  password reset.
- Rerun MinIO bootstrap after changing bucket policies or application secrets:

  ```bash
  docker compose --env-file <secrets-file> run --rm --no-deps minio-bootstrap
  ```

- The operator's **Bus telemetry source** menu switches live/replay at runtime;
  it does not use `TELEMETRY_MODE` and does not require a Compose restart.
- The default recording path is always enabled. Relay, Node, and Vision must
  receive the same `NODE_INTERNAL_SERVICE_TOKEN`; mismatches cause recording or
  Android telemetry validation failures.
- `docker compose config --quiet` validates interpolation but does not prove
  GPU access, BIMS credentials, TURN reachability, or that the model file is
  compatible with the CUDA/TensorRT runtime.

## Basic checks

```bash
docker compose --env-file <secrets-file> ps
docker compose --env-file <secrets-file> logs --tail=100 node routing vision relay
docker compose --env-file <secrets-file> config --quiet
```

After startup, verify the operator URL at
`https://<TLS_PUBLIC_ADDRESS>:39001/operator/`, routing readiness through the
Node/Nginx health route, and the Vision log's selected CUDA device. For live
BIMS, select **Live BIMS** in the operator dashboard only after the key has
been supplied to Compose.
